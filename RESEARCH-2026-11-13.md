## Findings and recommended changes

### 1. AP2: replace the three-mandate explanation

**Location:** lines 278–285 and the trip example at 640–642.

The current documentation describes **two primary mandate types**, Checkout and Payment, each with **Open** and **Closed** stages. The README retains an “Intent Mandate” as a third current type even though it has updated Cart Mandate terminology elsewhere. Explain autonomous authorization through the open mandates and completion through the closed mandates. Also replace “tamper-proof” with “tamper-evident”; a signature does not guarantee that the original interpretation of a user's wishes was correct. [AP2 specification](https://ap2-protocol.org/ap2/specification/), [Checkout Mandate types](https://ap2-protocol.org/ap2/checkout_mandate/), [Payment Mandate types](https://ap2-protocol.org/ap2/payment_mandate/).

The travel example should be explicitly illustrative. AP2 does define a budget constraint used with agent recurrence, with evaluation requiring tracking previous mandate presentations. The example should explain who maintains that state before claiming enforcement of a shared travel budget. Coordinating several bookings alone does not establish an atomic, all-or-nothing transaction. This is a qualification of the example, not a claim that AP2 lacks budget controls. [Payment Mandate constraints](https://ap2-protocol.org/ap2/payment_mandate/).

### 2. ACP: correct maintainers, release terminology, and checkout operations

**Location:** the governance table, lines 194–204 and 232, line 628, and the partner roster.

The repository's `MAINTAINERS.md` lists **OpenAI, Stripe, and Meta** as lead maintainers. Its README still says OpenAI and Stripe, so cite the dedicated maintainer file and acknowledge the upstream inconsistency rather than retaining “originally co-created with Meta.” This verifies the named maintainers, not the date Meta joined or the historical co-creation claim. [Pinned maintainer file](https://raw.githubusercontent.com/agentic-commerce-protocol/agentic-commerce-protocol/7fdd78df677a94dce04c770644b0fbbb1401272b/MAINTAINERS.md).

Change “four endpoints” to **five checkout operations: create, update, retrieve, complete, cancel**. The schema actually contains four checkout paths and five method/path operations; its GET operation is named `getCheckoutSession`. The README's four-item list omits retrieve. Retain beta status and distinguish the published snapshot from `unreleased/`; calling the whole protocol stable goes beyond its stated maturity. [Pinned checkout OpenAPI](https://raw.githubusercontent.com/agentic-commerce-protocol/agentic-commerce-protocol/7fdd78df677a94dce04c770644b0fbbb1401272b/spec/2026-04-17/openapi/openapi.agentic_checkout.yaml).

### 3. ACP: reconcile Instant Checkout and remove the unsupported sales claim

**Location:** lines 200–214 and 653.

The introduction says ACP currently powers Instant Checkout, while the status section says the product was retired. Use historical wording for that initial experience and distinguish the protocol's checkout specification from ChatGPT's current product strategy.

OpenAI's 24 March announcement describes expanding ACP for discovery and allowing merchant-owned checkout experiences. It does **not** substantiate “five months of near-zero sales.” Digital Commerce 360's 6 March reporting includes direct company comments about shifting checkout to apps, but also does not supply that sales measurement. Treat the quantitative characterization as unverified, not disproven: omit it unless a credible, specifically cited source is added. Prefer the documented product shift over the stronger inference that ACP itself has narrowed to discovery. [OpenAI announcement](https://openai.com/index/powering-product-discovery-in-chatgpt/), [reporting with direct company comment](https://www.digitalcommerce360.com/2026/03/06/openai-shifts-checkout-plans-agentic-commerce-strategy/).

Also replace “solving the PCI compliance challenge” with a narrower description of reducing exposure to raw payment credentials. Tokenization is not blanket evidence of an integration's compliance.

### 5. MCP: remove the claim that implementing UCP or ACP requires MCP

**Location:** lines 483–490 and 624.

“If you are implementing UCP or ACP, you are implementing MCP” is incorrect. UCP supports REST and MCP, and ACP provides a REST API alongside its MCP binding. State that MCP is **one supported integration binding**. Any statement that it dominates observed storefronts must be attributed to a dated measurement and its sample. [Google's integration overview](https://developers.google.com/merchant/ucp), [ACP checkout OpenAPI](https://raw.githubusercontent.com/agentic-commerce-protocol/agentic-commerce-protocol/main/spec/2026-04-17/openapi/openapi.agentic_checkout.yaml).

The July MCP migration information is worth retaining. Add the official migration/release details rather than more general MCP tooling. [MCP release explanation](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

### 6. MPP: rewrite the comparison with x402

**Location:** lines 350–352 and 879.

Remove the blanket statement that MPP shares an EIP-3009/Permit2 signature substrate with x402. MPP defines a payment-method-independent HTTP authentication framework; the cryptographic mechanism depends on the payment method. Its specification index includes card, Stripe, Tempo, Lightning, and other methods. [MPP specification index](https://paymentauth.org/), [Payment HTTP authentication draft](https://paymentauth.org/draft-httpauth-payment-01.html).

Also remove the implication that usage-based payments or deferred settlement uniquely distinguish MPP from x402. Current x402 documentation includes `upto` usage-based charging and batch settlement. Compare concrete methods and SDK support instead of treating x402 as only an unstructured HTTP 402 response. [x402 Upto](https://docs.x402.org/schemes/upto), [x402 batch settlement](https://docs.x402.org/schemes/batch-settlement).

Move processor-specific minimum payment amounts out of the protocol summary, or explicitly tie each amount to its implementation and a verification date.

### 7. Web Bot Auth: an adopted working-group draft now exists

**Location:** lines 584 and 623.

Replace “no draft adopted” with: **“Active IETF working-group Internet-Draft; `draft-ietf-webbotauth-httpsig-protocol-01`, updated 29 October 2026. Not an RFC.”** The Datatracker explicitly marks it as a WG Document. Link the actual draft as well as the charter. [IETF Datatracker](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/).

Keep identity distinct from purchase authority: identifying an automated client does not, on its own, prove the shopper authorized a particular transaction.

### 10. EU AI Act: the high-risk timeline is wrong

**Location:** lines 976–977.

The blanket claim that high-risk obligations take full effect in August 2026 conflicts with the Commission's current account of the AI Omnibus, which gives **2 December 2027 for Annex III high-risk systems** and **2 August 2028 for high-risk systems embedded in regulated products**. It reports entry into force of the Omnibus on 27 July 2026. General applicability and transparency requirements must be distinguished from these high-risk dates. Attribute the replacement dates to the Commission: the linked EUR-Lex page returned HTTP 202 without readable legislative text during this check, so this audit did not independently inspect the enacted amendment. [Commission timeline](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai), [Omnibus entry into force](https://digital-strategy.ec.europa.eu/en/news/ai-omnibus-enters-force).

Do not imply that every shopping or payment agent is automatically high-risk. Classification depends on its use and the applicable category. Link official classification guidance instead of the third-party AP2 regulatory domain. [Commission classification guidance](https://digital-strategy.ec.europa.eu/en/policies/guidelines-ai-high-risk-systems).

## Suggested maintenance approach

First land the factual corrections and canonical-link fixes. Then add the implementation resources above within existing sections. Make product pruning a separate editorial change so readers can distinguish factual corrections from scope decisions.

Add a small “Verified on” date to each protocol's version/status summary, coupled to its official release or status source. Keep **spec version**, **implementation version**, **standardization stage**, and **commercial availability** separate. A quarterly review of those fields, plus checks for redirected destinations and new official release notes, will be more useful than continually appending news links.

## Evidence limits

This was a section-by-section curation and factual review, with targeted verification of specifications, release pages, maintainer files, browser documentation, standards-body publications, regulator material, and recent primary announcements. Regrounding added direct GitHub API checks, raw specification inspection, an immutable ACP revision, and a response-metadata record. Secondary trackers were used to discover leads, not as authority for technical corrections. Original reporting with direct company comment was used to cross-check the product-history claim.

It was not an exhaustive HTTP check of every README link, a conformance test of the linked SDKs, or a complete legal docket review.
